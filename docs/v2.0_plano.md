# Plano — Artigo v2.0: Validação em Base Dermatológica Brasileira

## Contexto

O artigo v1.1 (CBIS'26) está pronto para submissão e demonstra empiricamente que o pipeline híbrido CNN+classificador clássico funciona sobre HAM10000. Uma das limitações reconhecidas é o **viés étnico-fenotípico**: HAM10000 foi compilado na Áustria/Austrália, sub-representando fototipos III–VI predominantes no Brasil. Este v2.0 endereça essa lacuna construindo uma base brasileira a partir de dois livros didáticos nacionais e avaliando o mesmo modelo nesse domínio.

**Material disponível** em `docs/entregas/2.0_artigo_multimodal_base_nacional/material_base/`:
- `Dermatologia - Azulay - 6 ed. rev e atual. (2015) - Pt.pdf` (78 MB) — atlas dermatológico brasileiro de referência
- `PORTUGUEZ Glosario Ibero Latinoamericano de Dermatología 6a Edicion ... .pdf` (23 MB) — glossário ibero-latino-americano

**Pipeline reaproveitável** (do v1.1):
- Modelo treinado em `models/modelo_multimodal_final.keras` (76 MB) — não será re-treinado
- Cache de embeddings em `data/embeddings_cache/` (HAM10000 já extraído)
- Scripts: `scripts/_experimentos_cbis.py`, `scripts/experimentos_revisao.py`
- Convenção do CSV de metadados (do `data/nova_base/metadata_curada.csv`):
  - colunas: `image_id`, `dx`, `age`, `sex`, `localization`, `dataset_source`
  - `dx` em 7 classes HAM10000: `akiec`, `bcc`, `bkl`, `df`, `mel`, `nv`, `vasc`
  - `localization` em 15 categorias do vocabulário HAM10000

## Desafios estruturais identificados

1. **Livros NÃO têm metadados clínicos sistemáticos por imagem**: Azulay e Glossário não capturam por foto a tripla `(idade, sexo, localização)`. Em geral, ou ausentes ou em prosa descritiva.
2. **Mapeamento diagnóstico fuzzy**: livros usam terminologia médica detalhada (ex.: "Ceratose Solar pré-cancerosa, Bowen, Doença de Paget"), nem sempre 1:1 com as 7 classes HAM10000.
3. **Qualidade variável das imagens**: fotografias clínicas e dermatoscopias misturadas; resoluções diferentes; possivelmente JPEG com artefatos de impressão.
4. **Copyright**: livros são protegidos. Uso ACADÊMICO/PESQUISA é permitido (fair use), mas as imagens **não podem ser redistribuídas publicamente** — o dataset extraído deve permanecer privado (gitignored).
5. **Conjunto de teste, não de treino**: nem cogitar re-treinar nada com essas imagens. Apenas avaliação do modelo HAM10000 num novo domínio.

## Objetivo e critérios de sucesso

**Objetivo:** Construir uma base brasileira `data/base_nacional/` (N alvo: 200–500 imagens) com a mesma estrutura do CSV `metadata_curada.csv`, e avaliar o modelo HAM10000 (sem re-treinar) usando o pipeline existente, comparando degradação de desempenho com a Etapa 1.

**Sucesso = um artigo v2.0 capaz de responder, com evidência empírica:**
- Quanta degradação o modelo HAM10000 sofre em imagens brasileiras?
- O viés étnico-fenotípico predito teoricamente se manifesta nos dados?
- O pipeline híbrido (XGBoost sobre embeddings) preserva sua superioridade sobre a CNN end-to-end no novo domínio?

### Fase 1 — Extração de imagens dos PDFs (2-3 dias)
- [ ] Criar `scripts/extract_book_images.py` que usa `pymupdf` (PyMuPDF) para:
  - Iterar páginas de cada PDF
  - Extrair imagens embarcadas (`page.get_images()`)
  - Capturar texto adjacente (legenda, parágrafo) via `page.get_text("blocks")`
  - Salvar cada imagem como `{source}_p{page}_i{img_idx}.png` em `data/base_nacional/images_raw/`
  - Salvar `data/base_nacional/raw_extraction.csv` com colunas: `image_id`, `source_book`, `source_page`, `image_index`, `nearby_caption`, `nearby_text`, `width`, `height`
- [ ] Criar `scripts/filter_book_images.py` — **validador automático** (não exclui, só sinaliza):
  - Detecta lixo por heurística e adiciona colunas:
    - `lixo_pequena` (bool): largura ou altura < 100px
    - `lixo_uniforme` (bool): desvio padrão de pixels < limiar (imagens em branco, fundo único)
    - `lixo_escala_cinza` (bool): canal RGB com correlação > 0,99 (diagramas/esquemas)
    - `lixo_proporção_extrema` (bool): aspect ratio < 0,3 ou > 3 (logos, barras)
    - `lixo_score` (0-4): soma dos flags acima
  - Atualiza `raw_extraction.csv` com essas colunas
  - Imagens com `lixo_score >= 2` ficam **sinalizadas** mas **não removidas** — médico/usuário decide na curadoria
- [ ] Esperado: 500–2000 imagens brutas → após validador, ~200–500 com `lixo_score == 0` para revisão prioritária

### Fase 2 — Mapeamento diagnóstico via Claude Code (interativo, sem API key) (2 dias)
- [ ] **Modo de operação:** o LLM (Claude) que está rodando neste Claude Code é o classificador — não há `.env` nem chave de API separada. O usuário pede ao Claude para processar lotes (ex.: 50 linhas por turno) do `raw_extraction.csv`, e o Claude lê + classifica + escreve em `data/base_nacional/ai_inferred.csv`.
- [ ] Esquema de classificação (campo a campo, derivado da legenda `nearby_caption` + `nearby_text`):
  ```
  image_id          (PK, vindo de raw_extraction.csv)
  source_book       (Azulay | Glossario)
  source_page       (mantido para validação cruzada — usuário abre o PDF nessa página)
  dx_inferido       (akiec|bcc|bkl|df|mel|nv|vasc|outros)
  dx_original_texto (termo médico exato no livro, ex. "Doença de Bowen")
  localizacao       (texto livre em PT, ex. "face", "ombro" — ou vazio)
  idade             (número quando mencionado, vazio quando ausente)
  sexo              (male|female|vazio)
  fototipo          (I-VI quando mencionado, vazio caso contrário)
  confianca         (0,0–1,0 — autoavaliação do LLM)
  justificativa     (1 frase explicando a inferência)
  ```
- [ ] **Sem imputação nessa fase:** valores ausentes ficam vazios (`""`), NÃO preenchidos com mediana/`unknown`. A imputação só ocorre na Fase 4 dentro do script de avaliação.
- [ ] Fluxo interativo no Claude Code:
  1. Usuário: "processa as linhas 0-49 do raw_extraction.csv"
  2. Claude: lê CSV, classifica cada linha, escreve em `ai_inferred.csv` (append)
  3. Usuário inspeciona, valida, peça próximo lote
- [ ] **Revisão pontual humana** posterior: filtrar `ai_inferred.csv` por `confianca < 0,8` ou `dx_inferido == "outros"` e revisar (~30% esperado)
- [ ] Esperado: ~70% com `dx` em alta confiança auto-aprovado; ~30% requer revisão; ~30% com `localizacao` real; ~5% com `age`/`sex`; **bônus: ~10–20% com `fototipo`** (vantagem brasileira)
- [ ] Custo: zero (Claude Code já está rodando)

### Fase 3 — Curadoria e consolidação (3 dias)
- [ ] Revisão LLM + humana sobre `ai_inferred.csv`:
  - Subset de baixa confiança (`confianca < 0,8` ou `dx == "outros"`) → revisão manual
  - Usuário/estagiário pode abrir cada PDF na `source_page` para validar
  - Para casos confirmados como lixo (logo, diagrama escapou ao filtro), marcar `excluir=1`
- [ ] Consolidar em `data/base_nacional/metadata_base_nacional.csv` com schema final:
  ```
  image_id, dx, age, sex, localization,
  dataset_source (AzulayBook|GlossarioBook),
  source_book, source_page,
  raw_caption, nivel_confianca, fototipo,
  excluir (0|1)
  ```
- [ ] **NÃO imputar faltantes neste CSV** — `age`, `sex`, `localization`, `fototipo` ficam vazios quando ausentes. A imputação (mediana 50 para age, 2 para sex, 13/"unknown" para localization) é responsabilidade do script `evaluate_base_nacional.py` na Fase 4, no momento de montar o array clínico — mesmo padrão do `evaluate_nova_base.py` do v1.1.
- [ ] Justificativa do padrão: preservar os dados "crus" no CSV permite (a) análise de quantos campos estavam realmente ausentes, (b) re-processamento futuro com estratégias de imputação diferentes, (c) auditabilidade.
